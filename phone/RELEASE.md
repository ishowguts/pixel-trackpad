# Android builds and connection behavior

The default `./phone/build.sh` builds the development app, **Pixel Trackpad Dev**, with application ID `local.pixeltrackpad`. It includes debug instrumentation. `./phone/check.sh` remains the offline JVM check; device instrumentation is `adb shell am instrument -w local.pixeltrackpad/.MotionCheck`.

The explicit `./phone/build.sh --release` builds **Pixel Trackpad**, application ID `io.github.ishowguts.pixeltrackpad`, at `build/phone-release/pixel-trackpad.apk`. It is not debuggable and contains neither instrumentation nor MotionCheck classes. The Java package and fully qualified activity remain `local.pixeltrackpad.MainActivity`. Both profiles retain the existing pairing URL scheme and v1/v2 paths; Android may offer a choice of app when both are installed. Scan QR inside the desired app to avoid ambiguity.

Both profiles use version code **2**, version name **0.2.0-beta.1**. Change `phone/version.conf` for the next version. For an individual build, set both `ANDROID_VERSION_CODE` and `ANDROID_VERSION_NAME`; use the same values for both profiles. Android updates require an increasing version code and the same signing identity.

## Permanent signing identity

Run `./phone/build.sh --setup-release-key` exactly once before the first release build. Setup creates `.local/android-release` with mode 0700, a PKCS12 keystore `signing.p12` and a random password file `password`, both mode 0600. The alias is `pixel-trackpad`, with RSA 3072 and 10,000 days of validity. Passwords are passed to signing tools through files, never through command-line values. The PKCS12 store and key use the same password. The build reuses this identity and refuses missing, empty, or incorrectly protected signing files. Setup refuses an existing directory, including an incomplete setup; it never replaces an identity silently. The debug key is separate.

**A protected offline backup of both release signing files is required before wider distribution.** Make and verify that backup manually, keep access restricted, and retain it for future updates. Do not publish either file or put them in source control. Losing either file prevents signing updates with this identity. Restore the original files if missing; do not generate a replacement key for an existing release. No backup is created or copied outside this checkout by these scripts.

Each build verifies the signed APK's compiled manifest, package, version, debuggability, backup and cleartext flags, permissions, optional camera features, activity, pairing links, and instrumentation profile. It also inspects every DEX for MotionCheck classes. `apksigner` verifies the signature and prints the public certificate fingerprint. Compare the SHA-256 certificate fingerprint between release builds; private signing material should never be displayed.

## Separate app data

Release installs alongside development without uninstalling it. Android keeps their pairing, preferences, and files separate. Release requires initial pairing and its own calibration/settings; no private data is copied from development. Enter your existing gains and calibration in release if you want the same tuning. Existing development settings are unchanged. The Mac currently remembers one phone credential: forgetting that phone to pair release revokes the old credential on the Mac, while development's local data remains intact. Switching back then requires pairing that app again.

## Foreground recovery and receiver compatibility

A saved, usable pairing connects when the app resumes and has focus, unless connection intent has been turned off. Phone Disconnect persists that choice and cancels retries. Scan QR, Settings, and pairing turn connection intent off and expose the toolbar; pairing still requires explicit confirmation and Mac approval, then Connect. Pause, actual focus loss, lock, and destruction immediately release the socket, contacts, Wi-Fi lock and screen-on flag. They retain connection intent for the next foreground session. There is no background network service or CPU wake lock.

Transient failures retry after 0.5, 1, 2, 4 and 8 seconds. Only one connection attempt or scheduled retry is active. Further transient failures keep one foreground retry scheduled at the maximum eight-second delay while connection intent remains enabled; they do not disable it. The backoff counter saturates, so repeated failures cannot overflow it. A successful authenticated session resets backoff. Every fresh session or layout change requires a new finger-down. Certificate rejection stops recovery. The receiver's one-second inactivity bound, frame freshness limits, 250 ms phone heartbeat, four-frame ACK window and three-second ACK deadlines are unchanged.

The cause of reported open-and-untouched drops remains unproven; an untouched session stayed connected for several minutes during device observation. Connected sessions keep the screen awake. Explicit lock, pause or shutdown ends the session; reopening after sleep or restart can reconnect when connection intent remains enabled. Recovery does not keep the app alive in the background or establish the cause of idle drops.

Use the updated Mac receiver for automatic recovery after a session failure and calibrated full screen. The Mac scripts change for two essential reasons: its old EOF cannot distinguish deliberate Disconnect from a network drop, and normalized touch coordinates need the resized surface's physical scale. No gesture recognition or gain settings change.

The optional hello fields `recovery: true` and `automatic` negotiate these additions without changing protocol version 1. A capable receiver replies with `stop: true` and `surfaceScale: true` in `ready`. Explicit Mac Disconnect/Cancel, Forget, or a dry/live mode change sends a single `S` after authentication, then closes the session. Automatic admission stays blocked in that receiver process until the user selects Connect on the phone. A blocked automatic hello receives `{"type":"stopped"}` instead of `ready`; this also handles a lost stop byte. Forget revokes authentication as before. A receiver restart resets admission and always starts in dry run; phone intent still respects received stops. Recovery never enables live input.

Old phones receive the original ready response and EOF, with unchanged sample scaling. A new phone can still use an older receiver in toolbar mode, but full screen is unavailable and an established-session failure requires manual Connect, because that receiver cannot safely negotiate the new behavior. Initial connection failures use the same capped foreground retry delay. Update and rebuild the local Mac app with `./build.sh` to use the new features; no portable binary is rebuilt or published automatically.

## Full-screen calibration and controls

After authenticated connection to an updated receiver, the toolbar and its padding disappear and system bars hide. Android 11+ uses WindowInsetsController; Android 8–10 uses immersive flags. Navigation and cutout safety insets remain outside the active surface. The accessible Controls button stays in a safe corner and consumes its own touch. Controls reveals the toolbar immediately while retaining the connection; Full screen enters again. Back exits full screen first, including Android 13+ back dispatch. Failure, disconnect, pairing, scan and settings expose the toolbar and bars.

Calibrate the grey rectangle **with the toolbar visible**. The app sends normalized contacts plus the ratio between the current surface dimensions and that reference rectangle. The receiver applies this ratio before recognition, so more physical area is available in full screen without changing points/mm or fractional motion. Mode changes and resizing cancel the current gesture, discard unsent touches, and require a new DOWN. Contacts outside the active rectangle or on the overlaid Controls button cancel rather than clamp into an unintended drag. Remeasure the reference rectangle if the toolbar layout, display settings or device changes. The old saved physical dimensions may need remeasurement if the new toolbar changes the rectangle; do not change gains to compensate.

## Hardware validation and remaining checks

The debug-only MotionCheck extends the existing harness with production reconnect state and real Android control routing. Its activity uses separate disposable storage and an in-memory Link; it cannot contact the receiver or read the saved pairing. The final rebuilt debug APK, after the retry correction, passed MotionCheck on Pixel 5 with Android 14: Controls routing, Full screen, Back, resize cancellation/fresh DOWN, lifecycle, Wi-Fi lock and ACK checks, without a receiver connection or Mac input.

The signed release APK installed alongside development, launched cleanly, rejected run-as as not debuggable, and registered no instrumentation. Its installed SHA-256 matched the built APK. Release paired with the updated portable Mac app in dry mode. The connected full-screen touch area and Controls overlay were visually inspected; showing the toolbar retained authentication. Home released Wi-Fi locks with balanced acquisition/release counts and the Mac became idle. Reopening the phone automatically reconnected in full screen without Connect. Mac Disconnect stopped automatic reentry; explicit Connect restored full screen. Closing and reopening the receiver window also recovered automatically through Bonjour, with the receiver still in dry mode.

The original untouched-idle drop cause remains unproven. Live input and physical sensitivity comparisons remain unverified. Reboot recovery, an actual Wi-Fi outage, lock/unlock, broader interruption and pairing flows, and Android 8–10 fallback still require physical checks. These results do not establish OS low-latency activation or smooth live gestures.
